## 1. 측정 기반 (headless)

- 노드를 **headless(구독 모드, `debug_mode:=false`)** 로 실행하고 bag `7_to_hoamji`(`/camera/image_rect`, 2237 frames)를 재생 → `/camera/lane_result`(`fo_msgs/Cam2LD`) 수집.

- rate 2 기준 **1318 프레임** 처리분 통계 + rate 1.5 원시값 샘플링.

> **중요:** 본 진단은 **headless 구독 경로**를 측정한 것이다. 이후 노드에 추가된 렌더 캐싱 최적화(`panel_cache_`/`info_cache_`/`bev_cache_` + `panel_dirty_`/`frame_updated_`/`overlay_dirty_`, `syncClosedWindows()`)는 **전부 `if (debug_mode_)` 가드 내부의 GUI/디버그 뷰어 전용**이며 headless 경로를 건드리지 않는다(`yolopv2_cam2_node.cpp:1022,1030,1049,1064`). 따라서 아래 P5 처리량 결론은 이 최적화의 영향을 받지 않는다.

## 3. 문제점 (P1~P5)

### P1. Cam2LD 계수→필드 매핑 off-by-one — 치명 · `stale-refs-corrected`

원 진단은 `helper_lane.cpp:37-53`의 인라인 `coeffs[...]` 매핑을 근거로 들었으나, 해당 파일은 이후 리팩터링되어 명명 변수(`left_pos`/`left_heading`/`left_model_a`/`left_model_da`)를 사용한다. **정정된 현재 코드 근거는 `helper_lane.cpp:36-39, 60-80`.**

현재 `buildCam2LD`의 매핑:

```cpp
// helper_lane.cpp:36-39  (coeffs_L[i] 추출)
left_model_a  = coeffs_L[0];   // x³ 계수
left_heading  = coeffs_L[1];   // x² 계수
left_pos      = coeffs_L[2];   // x  계수  (기울기)
left_model_da = coeffs_L[3];   // 상수항    (x=0 횡offset)

// helper_lane.cpp:60,70,73  (필드 채움)
lane_mark_position     = left_pos;        // = coeffs[2]  ← x-계수(기울기)
lane_mark_heading_angle= left_heading;    // = coeffs[1]  ← x²-계수
lane_mark_model_a      = left_model_a;    // = coeffs[0]
lane_mark_model_da     = left_model_da;   // = coeffs[3]  ← 실제 횡위치가 여기 들어감
```

다항식 차수 규약은 소비 코드에서 확인됨(`LaneDetection.cpp:514-517, 1020, 1343, 1530`):

```cpp
y = coeffs[0]*x³ + coeffs[1]*x² + coeffs[2]*x + coeffs[3];
```

즉 차량 원점 x=0에서 **횡위치 = coeffs[3](상수항)**, **heading = dy/dx = coeffs[2](x-계수)**. 그런데 현재 `lane_mark_position`에는 coeffs[2](기울기)가, `lane_mark_model_da`에는 coeffs[3](횡위치)가 들어간다.

**결론: 변수명만 바뀌었을 뿐 off-by-one은 현재 코드에도 그대로 존재한다.** 실측 증거(정상 프레임 f45: `pos=0.14, head=-0.02, a=0.0007, da=1.32`) — 물리적 횡offset(≈1.3 m)이 `model_da`에, `position`에는 기울기(0.14)가 들어가 있어 일관됨. 하위 소비단(SF/planning)이 위치·heading을 잘못 받는 구조.

### P2. degenerate fit이 GOOD로 통과 — 심각 · `재확인 필요`

view_range가 극소(0.1~1.7 m)인데 품질 GOOD로 발행되는 프레임 존재.

**실측 증거:** `f15 L: q=GOOD pos=-607.53 head=115.23 a=-5.32 da=-172.74 vr=0.1` / `f195 L: da=1620.22 vr=1.3` / `f210 R: da=-835.41 vr=1.3`. 근거리 소수 픽셀만 잡혔을 때 3차 피팅이 ill-conditioned가 되어 고차 계수가 폭발, RMSE는 작아 게이트 통과. 통계 std를 수백~수천으로 키우는 주범.

> **재확인 필요:** `개발보고서_개선방안.md §0`은 P2 게이트/차수 강등이 반영되어 "C ✅ 구현(pos_std 1189→6.2)", "D2 ✅ 성공(pos_std→3.2)"이라 주장하나, 그 근거로 든 심볼(`roi_top_ratio`, `runBagDump`, `linearRefit`, `degenLatY`)은 **현재 소스에 하나도 존재하지 않는다**:
>
> ```bash
> grep -rn "roi_top_ratio\|runBagDump\|linearRefit\|degenLatY" src/ws_cam2/src/lane_detection
> # (매치 없음)
> ```
>
> 따라서 "degenerate 게이트/차수 강등 반영 완료" 주장은 **현재 코드 기준으로 미확인**이다(코드 근거 심볼 부재). 게이트 로직 자체는 `trackLaneGeometryKF()`/`resultsFromRawFit()` 경로와 `x_check` 예측(`LaneDetection.cpp:3144-3145`)에 존재할 수 있으나, 개발보고서가 인용한 심볼로는 검증 불가하므로 재확인 대상.

### P3. 출력 필드 미구현 (width/type/color) — `confirmed`

`lane_mark_width=0xff`, `lane_mark_type=0xff`, `left/right_lane_color_information=0xff` 하드코딩. 근거: `helper_lane.cpp:58,62,64,68,87,88`. 차선폭/실선·점선/색상 정보를 하위단이 사용 불가.

### P4. 원거리 커버리지 부족 — `stale-refs-corrected`

view_range 중앙값 ~10 m. 원 진단은 `roi_xmax=70 m` 대비 낮음이라 했으나, 실제 설정 `yaml/kcity.yaml:39`은 **`roi_xmax: 30.0`** 이다(헤더 기본값 `LaneDetection.hpp:71`은 70.0이지만 yaml이 오버라이드). **정정: 유효 전방 ROI 상한은 ~30 m.** 그래도 view_range ~10 m는 30 m 상한의 1/3 수준이라 원거리 마스크/피팅 약화는 유효한 문제. 갭 원인(마스크 far-field 소실 vs 피팅 조기 종료) 분리 진단 필요.

### P5. 처리량/실시간성 — `confirmed`

처리량 약 **20 fps**(1318 frames / ~67 s @rate2). 소스 native ~16.7 fps → 1x는 여유, 1.5~2x에서 프레임 드롭(~40%). QoS `keep_last(1)` 단일 스레드라 부하 시 최신 프레임만 처리(드롭). **§1의 렌더 캐싱은 GUI 전용이므로 이 처리량을 개선하지 않는다 — 캐싱으로 throughput이 해결됐다고 오해 금지.** 실서비스 프레임레이트 확정 필요.

## 5. 해결안

### P1 (즉시)
- `buildCam2LD` 매핑을 물리 정의에 맞게 교정: `lane_mark_position = coeffs[3]`(횡위치), `lane_mark_heading_angle = coeffs[2]`(heading). `model_a`/`model_da`는 메시지 스펙과 곡률/곡률변화 정의 재확인 후 확정.
- **주의:** 하위 소비단(SF/planning)이 현재의 잘못된 매핑에 이미 맞춰져 있을 수 있음 → 스펙 문서·소비 코드와 **동시 반영**해 한쪽만 고쳐 깨지지 않도록. 외부 UDP 규약 확보가 선행조건.
- 검증: headless 분석 스크립트로 position std가 정상(≤ 수 m)으로 떨어지는지 재측정.

### P2 (즉시)
- degenerate 게이트: `view_range_m < valid_view_range`(예 5 m) 또는 `span_m` 미달 시 NODET/availability=0 강제.
- 계수 sanity 클램프: `|d| > lane_w_max*2`, `|c|`·`|a|` 임계 초과 시 reject. `rmse_hard_bad_m`만으로 부족 → 저-span·고-곡률 조합 게이트 추가.
- 근본: 점 수/커버리지 부족 시 3차 대신 1~2차로 차수 자동 강등(overfit 방지).
- **먼저** 현재 게이트/강등 로직이 실제로 어디에 있는지(또는 부재한지) 코드로 재확인.

### P3 (중기)
- `lane_mark_width`: 좌우 동시 검출 시 `|d_L - d_R|`로 산출.
- `lane_mark_type`: 마스크 세로 연속성(런길이/공백비)으로 실선/점선 분류.
- 색상: HLS 흰/황 게이트(`hls_white_*`/`hls_yellow_*`) 결과 반영.

### P4 (중기)
- BEV 원거리 해상도/`strip_*` 재튜닝, 마스크 far-field 임계 완화.
- `roi_xmax`(≈30 m) 대비 유효 range(~10 m) 갭 원인 분리 진단(마스크 소실 vs 피팅 조기 종료).

### P5 (중기)
- 목표 프레임레이트 확정 후 초과 시 추론 스레드 분리 or 입력 다운스케일 검토.
- `log_process_time` 활성화로 단계별 처리시간 프로파일.
